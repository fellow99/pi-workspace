# overall-spec.md — Pi Desktop Workspace 整体规格

> **层级：** 父工程 · 技术无关
> **版本：** v0.12.1 基线 ｜ **最后更新：** 2026-10-31
> **读者：** 产品、架构、测试、四个子工程的实现者。
> **规则：** 本文只描述 **WHAT / WHY**，不写框架、文件路径与实现细节；实现见各子工程 `spec.md` / `plan.md`。
> 需求编号：`FR-000-<三位数>`；动作词：**MUST** / **MUST NOT** / **SHOULD** / **MAY**。

---

## 1. 系统目的与用户

### 1.1 目的

把开源 agent harness **Pi** 与其浏览器界面 **Pi Web** 封装为四类“开箱即用”的桌面/移动应用，
让用户**不需要手动启动服务、配置端口、打开浏览器**，直接获得完整的 agent 对话、工具、会话与扩展体验。

### 1.2 目标用户

- 在 Windows / macOS / Linux 上工作的开发者、研究者、知识工作者（Desktop）。
- 在 HarmonyOS PC / 平板上工作的用户（HOS / Ark）。
- 在 Android 手机 / 平板上使用的用户（Android）。
- 需要本地数据、可控模型 Provider、可扩展工具链的用户。

### 1.3 四种产品形态（用户视角）

| 形态 | 使用场景 | 关键差异（用户可感知） |
|---|---|---|
| **Pi Desktop** | 桌面全功能 | 托盘、原生通知、终端/PTY、系统 git、检查更新 |
| **Pi Desktop · Electron on HarmonyOS 版** | 鸿蒙 PC / 平板，保留桌面 API | 原生窗口、托盘能力受限、无系统 git、纯 JS 工具顶替 |
| **Pi Desktop · HarmonyOS 版** | 鸿蒙设备，包体更小 | 系统 WebView、无 Electron、JITless、部分能力受限 |
| **Pi Desktop · Android 版** | Android 手机 / 平板 | 系统 WebView、前台服务、SAF、git/pnpm 扩展、无 PTY |

## 2. 用户故事

- 作为用户，我安装应用后**双击即可开始对话**，不需要启动命令行或浏览器。
- 作为用户，我的模型选择、API Key、会话、设置**保存在本机**，重启后恢复。
- 作为用户，我可以在对话中让 agent 读写文件、执行命令、搜索代码、使用 Git。
- 作为用户，我在移动端也能选择工作区、上传文件、收到通知、把外链交给系统浏览器。
- 作为用户，我在四个版别看到**同一个品牌、同一个界面、同一套会话格式**。
- 作为维护者，我能用同一个上游版本、同一套规格，构建出四个版别并逐项验收。
- 作为审核者，我能从文档追溯到源码、真机证据与发布产物。

## 3. 功能需求

### 3.1 启动与就绪

- **FR-000-001**（MUST）：应用启动后必须自动准备运行时与本地服务，用户无需手动启动。
- **FR-000-002**（MUST）：启动过程必须可观测（阶段文本/进度/日志），失败时必须显示可读错误与诊断入口。
- **FR-000-003**（MUST）：本地服务必须使用随机端口并只绑定本机（或按平台需要绑定局域网并启用密码）。
- **FR-000-004**（MUST）：应用必须单实例运行；重复启动必须唤回已有窗口/实例。
- **FR-000-005**（MUST）：首启必须完成载荷就位；二次启动必须幂等（内容未变不重复解压）。
- **FR-000-006**（MUST）：应用退出必须优雅关闭服务与连接；超时必须有兜底强退。

### 3.2 对话与模型

- **FR-000-007**（MUST）：用户必须能创建会话、发送消息、接收流式回复、中断/重载。
- **FR-000-008**（MUST）：用户必须能配置模型 Provider、API Key、默认模型，并测试连通性。
- **FR-000-009**（MUST）：会话必须以可恢复的形式持久化；应用重启后会话列表与内容可恢复。
- **FR-000-010**（MUST）：用户必须能导出会话；导出在四个版别均可用的路径下必须成功或给出明确原因。
- **FR-000-011**（SHOULD）：支持图片附件与视觉识图；不支持时必须明确提示。

### 3.3 工具与扩展

- **FR-000-012**（MUST）：agent 必须能读写文件、列目录、搜索文件与内容、执行 shell 命令。
- **FR-000-013**（MUST）：平台缺少系统工具时，必须用随包扩展**同名顶替**，不得静默失败。
- **FR-000-014**（MUST）：工具失败必须返回结构化错误与原因，不得伪造成功。
- **FR-000-015**（SHOULD）：支持 Git 工具组（状态、diff、提交、克隆等）；平台无系统 git 时用纯 JS 实现。
- **FR-000-016**（SHOULD）：支持 MCP 服务器（HTTP/SSE 优先；stdio 按平台能力）。
- **FR-000-017**（MUST）：项目信任门禁必须生效（ask / allow / deny），默认 `ask`。
- **FR-000-018**（SHOULD）：支持插件 / 技能 / 扩展的本地装载；在线安装按平台与合规策略。

### 3.4 文件与工作区

- **FR-000-019**（MUST）：用户必须能选择工作区目录，并在会话中使用该目录。
- **FR-000-020**（MUST）：工作区访问必须有围栏（只能向下浏览/读写允许的根）。
- **FR-000-021**（MUST）：移动端必须使用平台文件选择器/授权模型；不得申请不必要的全盘权限。
- **FR-000-022**（SHOULD）：支持多根（沙箱、文档、下载、桌面）并让 agent 感知。

### 3.5 平台能力

- **FR-000-023**（MUST）：外链必须交系统浏览器打开；应用内不得内嵌任意网页。
- **FR-000-024**（MUST）：通知能力可用时必须能通知会话完成；不可用时必须如实说明。
- **FR-000-025**（MUST）：桌面端必须提供托盘/窗口生命周期；移动端必须处理返回键/前后台。
- **FR-000-026**（SHOULD）：移动端支持前台服务/后台保活；桌面端不强制。
- **FR-000-027**（SHOULD）：终端/PTY 在支持的平台可用；不支持时明确 `unsupported`。
- **FR-000-028**（MUST）：应用必须显示“内容由 AI 生成”标识（移动端合规要求）。

### 3.6 品牌与版本

- **FR-000-029**（MUST）：四版必须使用统一品牌 **Pi Desktop**（允许渠道后缀，但用户可见主名一致）。
- **FR-000-030**（MUST）：品牌物料必须来自唯一来源；不得出现上游 `Pi Web` 用户可见文案或占位图标。
- **FR-000-031**（MUST）：技术标识符（包名、`pi-web`、`PI_WEB_*`、存储 key、路由）不得因品牌化改变。
- **FR-000-032**（MUST）：版本号必须可追溯；应用版本与上游版本分离时必须在文档中写明。
- **FR-000-033**（MUST）：发布产物必须可追溯到上游 tag/commit、运行时版本与补丁集。

### 3.7 构建与发布

- **FR-000-034**（MUST）：构建必须可复现：清理后仅靠源码 + 上游 tag + 运行时归档即可产出等价包。
- **FR-000-035**（MUST）：构建必须有门禁（类型、smoke、引擎校验、补丁可逆、品牌残留、合规）。
- **FR-000-036**（MUST）：发布必须带校验和；签名材料与密钥不得入库。
- **FR-000-037**（MUST）：构建/发布失败必须显式失败，不得产出半成品包。

### 3.8 文档与治理

- **FR-000-038**（MUST）：父工程与子工程 `specs/` 必须按宪法分工与编号规则维护。
- **FR-000-039**（MUST）：每个模块必须有 `spec.md` + `plan.md`；`plan.md` 回引 FR。
- **FR-000-040**（MUST）：每条结论必须可追溯到源码/配置/证据；不得留 `TODO` / `TBD`。
- **FR-000-041**（MUST）：提交必须使用 Conventional Commits 前缀；评审按请求/接收评审流程执行。

## 5. 非功能需求

### 5.1 性能与资源

- **NFR-000-001**：首屏在目标设备上应可接受（桌面 ≤ 数秒；移动端首次解包更久，必须有进度）。
- **NFR-000-002**：载荷解压必须流式/低内存，不得把整个归档读入内存。
- **NFR-000-003**：应用包体应尽量小；能用系统 WebView 的版本不随包 Chromium。
- **NFR-000-004**：长会话/SSE 不得泄漏连接；退出时应关闭。

### 5.2 安全与隐私

- **NFR-000-005**：服务只绑 loopback（或按需绑定局域网 + 随机密码）；凭据不落日志。
- **NFR-000-006**：渲染隔离、导航围栏、外链分流、生产无调试入口。
- **NFR-000-007**：最小权限；声明面必须有调用点；移动端权限运行时申请。
- **NFR-000-008**：API Key / 签名材料 / 设备标识不入库；提交前扫描。

### 5.3 可靠性与可观测

- **NFR-000-009**：启动失败必须可见（阶段 + 错误 + 日志）；不得白屏或静默退出。
- **NFR-000-010**：崩溃必须留痕（日志/最后错误）；移动端明确提示重启。
- **NFR-000-011**：关键路径（就绪、鉴权、载荷、引擎）必须有可重复的探针/门禁。

### 5.4 兼容性与国际化

- **NFR-000-012**：UI 继承上游多语言；品牌名替换不得破坏技术标识符。
- **NFR-000-013**：移动端旧 WebView 需 polyfill（如 `Intl`）；桌面/鸿蒙按运行时能力。
- **NFR-000-014**：四版会话格式、配置格式、目录约定保持一致，便于迁移。

### 5.5 可维护性

- **NFR-000-015**：上游零 fork；补丁幂等可逆；升级走版本模块。
- **NFR-000-016**：文档与源码同步；编号/目录/FR 三处一致。
- **NFR-000-017**：构建脚本可读、可复现、失败可见；不依赖本机隐式状态。

## 6. 系统边界

### 6.1 在范围内

- 四版的装配、构建、打包、签名、发布。
- 上游 `pi` / `pi-web` 的集成、载荷组装、补丁、品牌化。
- 平台能力桥（权限、选择器、通知、外链、日志、PTY）。
- 版本、构建、品牌、文档治理。

### 6.2 不在范围内

- 修改上游 `pi` / `pi-web` 的功能与 UI 设计。
- 自建模型服务、账号体系、云端同步、遥测服务。
- 应用商店上架材料的具体提交（各子工程 107 合规清单负责准备）。
- 官网内容与运营（`pi-desktop-website` 独立工程）。
- 父工程 `API.md` / `overall-api.md` / `overall-data-model.md` / `overall-test-cases.md`（明确不写）。

### 6.3 外部依赖

- 上游 tag `pi` v1.2.0 / `pi-web` v0.12.1。
- ohpm：`@fellow99/node-bridge` 0.1.0 / `@fellow99/node-runtime` 24.2.0。
- Maven Central：`io.github.fellow99:node-bridge` 0.2.0 / `node-runtime` 24.22.1。
- 模型 Provider API（DeepSeek 等）与网络。
- 品牌物料 `assets/`。

## 7. 假设与约束

- 四个子工程必须位于同一父目录，构建脚本依赖 `../pi`、`../pi-web`、`../assets`。
- 上游 API/行为可能变化；升级必须走 `011` 并重跑门禁。
- 移动端设备能力差异大；缺口必须如实登记，不以“理论可用”当验收。
- 签名材料由发布者本地持有；CI 通过 secrets 注入。
- 应用版本 `0.1.0`（Ark/Android）是预发布，不代表功能不完整。

## 8. 验收总则

1. **可证伪**：每条 FR 对应至少一个可观测判据（HTTP、文件、截图、日志字段、哈希）。
2. **分版验收**：四版分别验收，不以一版通过推定其它版。
3. **真机优先**：移动端以真机为准；模拟器只做轻量探针。
4. **证据归档**：真机记录、日志、截图、run id 必须可追溯。
5. **文档闭环**：实现变更必须回写 `specs/` 与能力清单；未回写视为未完成。
