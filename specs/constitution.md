# constitution.md — Pi Desktop Workspace 宪法原则

> 本文件是**父工程**的不可协商原则：模块编号、文档分工、源码即真理、上游零改动、提交与评审纪律。
> 各子工程 `constitution.md` 在本文件之下补充本工程的技术原则；冲突时以本文件的编号/分工规则为准，
> 技术事实以源码为准。
>
> **版本：** 1.0 ｜ **生效日期：** 2026-10-31 ｜ **适用范围：** `pi-workspace` 及四个产品子工程
> （`pi-desktop`、`pi-desktop-hos`、`pi-desktop-ark`、`pi-desktop-android`）。

---

## 第一条 模块编号规则（强制）

### 1.1 `0XX` —— 各子工程公共、共同的需求模块

只用于**跨工程共同**的需求。父工程 `specs/` 与各子工程 `specs/` 使用**相同编号**，父工程写共同规范，
子工程写本工程实现。

| 编号 | 模块 | 规则 |
|---|---|---|
| **`011-version-<VERSION>`** | 版本更新 | 历史编号 `101-version-<VERSION>` **统一改为** `011-version-<VERSION>`；父工程与子工程都使用 `011`，**不再创建** `101-version-*`。`<VERSION>` 为上游发布版本（当前 `0.12.1`）；历史版本目录保留、以 `<VERSION>` 区分，不重编号。 |
| **`012-building-workflow`** | 构建工作流 | 桌面（`pi-desktop`）与 Android（`pi-desktop-android`）适用；**鸿蒙工程暂无此模块**（`pi-desktop-hos` / `pi-desktop-ark` 使用各自本地 hvigor 构建，不建 `012`）。父工程 `specs/012-building-workflow/` 只写跨工程构建要求，不替代子工程构建文档。 |
| **`013-branding`** | 品牌化 | **四个子工程都必须有**。已有 `012-branding` / `103-branding` 等编号的，统一迁移为 `013-branding`；没有的必须补充 `spec.md` + `plan.md`。父工程 `specs/013-branding/` 写统一品牌口径与四版落点。 |

**解释：**

- `0XX` 是**保留段位**，不得再分配给工程内部模块；工程内部模块一律使用 `1XX`。
- 版本模块的 `<VERSION>` 是模块实例标识，不是编号复用；同一 `011` 下允许多个历史版本目录。
- 父工程 `011` 的目录名必须是 `011-version-0.12.1`（与子工程一致），不是 `101-version-0.12.1`。

### 1.2 `1XX` —— 各工程自己的基础功能模块

- 用于**本工程特有**的基础能力（启动、渲染、宿主能力、鉴权、工具、合规、平台适配等）。
- 因为各工程基础能力有共通部分，**尽量对齐编号，基准是 `pi-desktop-android`**：

| 编号 | 基准含义 | 对齐要求 |
|---|---|---|
| `101` | 运行时接入 / 启动编排 | 四版尽量使用 101 表示“接入运行时并启动” |
| `102` | 载荷流水线（组装 / 裁剪 / 投放） | 有载荷组装的工程优先用 102 |
| `103` | 渲染壳（WebView / ArkWeb / BrowserWindow + 页面） | 有独立渲染壳的工程优先用 103 |
| `104` | 宿主能力桥（权限 / 选择器 / 外链 / 通知 / 日志） | 有平台能力桥的工程优先用 104 |
| `105` | 鉴权（loopback / Cookie / 密码） | 鉴权独立成模块时用 105 |
| `106` | 工具与扩展（同名顶替 / 预设） | 工具扩展独立成模块时用 106 |
| `107` | 合规与安全 | 上架/隐私/权限清单用 107 |
| `108+` | 平台特有职责 | 托盘、通知、JITless、签名身份等 |

- 允许跳号；不允许为了“凑齐”而虚构模块。
- 未生成的模块**不占号**；生成时再按本表分配。

### 1.3 `2XX` —— 各工程的补丁、插件模块

- 用于**补丁、插件、扩展**（不是基础能力）。
- 各工程插件有共通部分，**尽量对齐编号**：

| 编号 | 含义 | 说明 |
|---|---|---|
| `201` | 插件运行时 / 扩展投放 | 桌面可选档 |
| `203` | 目录 / 工作区选择器插件 | HOS 已用；Ark/Android 如独立成模块可复用 |
| `204` | Git 插件 | HOS 单一事实源，Ark/Android 同构同步 |
| `205` | pnpm 插件 | Android 已实现，如独立成模块使用 |
| `206` | PTY / 终端插件 | 评估中；未产品化前不占号 |

- 补丁集本身按**被 patch 的上游 tag** 建目录（`patches/v0.12.1/`），不以 `2XX` 编号替代补丁目录。

### 1.4 编号纪律

1. **只增不改、不复用**；作废编号留空，不回收。
2. **模块编号 ⇄ 目录名 ⇄ `FR-<module>-*`** 三处必须一致。
3. 新增模块必须先改父工程本宪法/子工程 `specs/README.md` 与 `SPECS_CHECKLIST.md`，再建目录。
4. 编号迁移必须用 `git mv` 保留历史，并在子工程 `specs/README.md` 写迁移对照表。
5. `FR` 条目只追加不修订；作废条目标注 `[SUPERSEDED by FR-xxx-nnn]`。

## 第二条 规范文档分工（强制）

| 文档位置 | 关注点 | 必须写 | 不写 |
|---|---|---|---|
| **父工程 `specs/`** | 整体规划、整体设计、跨工程共同需求 | 四版定位、共同架构、版本矩阵、构建/品牌总规范、编号与分工 | 单个子工程的具体文件路径、内部实现细节、真机日志 |
| **子工程 `specs/`** | 本工程具体技术实现、独立需求 | 模块 `spec.md` / `plan.md`、本工程架构、数据模型、测试用例、证据引用 | 重复父工程的整体规划；复制 `docs/` 的论证过程 |
| **子工程 `docs/`** | 操作手册、工程规划、能力清单、真机记录 | 构建/运行步骤、完整论证、证据、设备矩阵 | 作为 `specs/` 的替代（`specs/` 必须自成体系） |

**结论：** 父工程管“为什么做、四版共同做什么”；子工程管“本工程怎么做、验收证据是什么”。

## 第三条 父工程文档集合（强制）

父工程 `specs/` 必须且只必须包含：

```
specs/
├── README.md              # 项目介绍、文档索引
├── STRUCTURE.md           # 整个项目目录文件结构
├── TECH.md                # 整个项目技术选型
├── ARCHITECTURE.md        # 整个项目整体架构
├── constitution.md        # 本宪法
├── overall-spec.md        # 整体规格
├── overall-plan.md        # 整体技术方案
├── 011-version-<VERSION>/ # 公共模块：版本更新
│   ├── spec.md
│   └── plan.md
├── 012-building-workflow/ # 公共模块：构建工作流
│   ├── spec.md
│   └── plan.md
└── 013-branding/          # 公共模块：品牌化
    ├── spec.md
    └── plan.md
```

**父工程不写** `API.md`、`overall-api.md`、`overall-data-model.md`、`overall-test-cases.md`：

- 数据面由上游 `pi-web` 提供，父工程不自有 API；
- 数据模型与测试用例落在各子工程 `specs/`；
- 这是明确取舍，不是缺漏；不得为“看起来完整”而补空文档。

## 第四条 源码即真理与证据纪律

1. **源码即真理**：每条结论必须能追溯到源文件、配置或命令输出；文档与源码冲突时以源码为准，并回改文档。
2. **证据标记**：
   - `✅` 已核实（读源码/配置/实测，附出处）
   - `🔶` 沿用（引用兄弟工程/上游结论，本工程未复现）
   - `⬜` 待验证（写明验证方式与时限）
   - `⚠️` 冲突/风险（两份材料互斥或硬阻塞）
3. `🔶` 不得当作本工程实测事实；`⬜` 在拿到证据前不得写成结论。
4. **可证伪验收**：每条验收写成“能观测到 X”（HTTP 200 / 文件存在 / 截图 / 日志字段），不用“应该可以”作为判据。
5. **禁止占位**：不写 `TODO` / `TBD` / 空标题；未定事项写 `⬜` + 验证方式 + 决策时限。
6. **历史保留**：旧版本结论、旧真机记录、旧能力数值不回改；迁移只改编号与引用。

## 第五条 上游零改动与补丁纪律

1. **不 fork** `pi` / `pi-web`；四版只装配，不改上游源码。
2. 补丁必须**按被 patch 的 tag** 归档（`patches/v0.12.1/`），不得跨 tag 复用。
3. 补丁必须**幂等 + 可逆**：
   - 应用前 `git apply --reverse --check`，已应用则跳过；
   - 应用 → 反向 → 逐文件 SHA-256 还原断言；
   - 冲突即终止，**禁止 `--3way`**。
4. 新补丁必须有可复现的失败证据；不得为“看起来完整”而加补丁。
5. 补丁数、语义断言、真机证据必须写回子工程 `specs/` 与 `patches/README.md`。
6. 品牌化、裁剪、文案替换只允许在**本工程产物副本**上进行。

## 第六条 架构原则（强制）

1. **进程内宿主**：Node + `pi-web` 跑在应用进程内；不引入子进程 Node（构建脚本除外）。
2. **同源 HTTP/SSE**：渲染层只通过 `http://127.0.0.1:<port>/` 访问数据面；无 CORS、无自定义协议、无 IPC 数据载体。
3. **薄壳**：壳只做启动编排、环境装配、窗口/WebView、平台能力、生命周期、错误可见；业务逻辑留在上游。
4. **随机端口 + 单实例**：端口 `listen(0)` 或先探后用；单实例是端口与数据目录唯一性的前提。
5. **失败可见**：启动阶段文本、错误页、日志、诊断入口必须至少有一个可观测；不允许静默降级。
6. **鉴权最小面**：loopback + 随机端口；需要跨进程访问时用随机密码；密码/凭据不入日志。
7. **平台真相**：能力缺口如实上报（`unsupported` + 原因），不伪造成功。
8. **数据本地**：无服务端、无账号、无遥测；模型 API 出网除外。

---

## 第七条 安全与隐私

1. **最小权限**：只申请实际使用的权限；声明面 ≠ 授权面，权限清单必须逐条有调用点。
2. **凭据不入库**：API Key、密码、keystore、签名口令、`auth.json` 不入库；日志只报长度/指纹。
3. **导航围栏**：主框架只允许同源；外链交系统浏览器；禁止内嵌任意网页。
4. **渲染隔离**：桌面 `sandbox: true` + `contextIsolation: true` + 无 `nodeIntegration`；预加载桥只承载壳层动作。
5. **生产无调试入口**：release 包不得带 `--inspect` / remote debugging；DevTools 仅 dev。
6. **敏感信息扫描**：提交前扫描密钥/口令/设备标识；发现即阻断。

---

## 第八条 版本、构建与发布

1. **上游钉住**：`pi` v1.2.0 + `pi-web` v0.12.1；CI 断言 tag 对应 commit SHA，重打 tag 即失败。
2. **运行时钉住**：ohpm / Maven 版本 + SHA-256；升级必须同时改锁文件与文档。
3. **应用版本与上游版本分离**：桌面/HOS 为 `0.12.1`，Ark/Android 为 `0.1.0`；发布 tag `v0.12.1` 不注入 `versionName`/`versionCode`。
4. **`versionCode` 单调递增**；不得回退或复用。
5. **构建可复现**：清理中间产物后，仅靠源码 + 上游 tag + 运行时归档即可产出等价包。
6. **门禁**：类型检查、smoke、引擎 SHA/ELF、补丁可逆、品牌 0 残留、合规检查；失败即阻断。
7. **发布证据**：Release URL / run id / HAP/APK 哈希 / 真机记录必须可追溯。

## 第九条 提交纪律（git-commit 技能）

1. 所有提交必须使用 **Conventional Commits** 前缀，且只能是：
   `feat` · `fix` · `docs` · `style` · `refactor` · `perf` · `test` · `build` · `ci` · `chore` · `revert`
2. **禁止其它前缀**（如 `development:`、`testing:`、`code-review:`、`update:`、`add:`）。
3. 格式：`<type>[optional scope]: <description>`；描述用现在时、祈使语气、<72 字符。
4. 破坏性变更：`feat!:` 或 `BREAKING CHANGE:` footer。
5. 不提交构建产物、日志、密钥、`node_modules` / `oh_modules`。
6. 不修改 git config；不强制推送 main/master；不跳过 hooks；不 amend 已推送提交。
7. 子工程与父工程**分别提交**：子工程先提交模块文档，父工程再提交 submodule 指针。

## 第十条 评审纪律（requesting-code-review / receiving-code-review）

1. **评审时机**：完成一个模块/一批文档后、合并前、发布前；重大重构前。
2. **请求评审**：按 `requesting-code-review` 技能，给出 `BASE_SHA` / `HEAD_SHA`、变更说明、需求/规格路径；
   评审者只读，不改工作树。
3. **评审输出**：优势、问题（Critical / Important / Minor）、建议、结论（Ready / With fixes / No）；
   每个问题必须有 `file:line`、原因、修法。
4. **接收评审**：按 `receiving-code-review` 技能，先理解、再核实、再实施；不表演式认同；
   不盲改；不理解的条目先澄清；技术不正确时用证据反驳。
5. **闭环**：Critical 立即修；Important 合并前修；Minor 登记；修复后重跑门禁并更新评审记录。

## 第十一条 规范文档方法（specs-as-built）

1. 规范文档按 **specs-as-built** 方法生成：先读源码/配置，再写文档；不猜测未读代码。
2. 每个模块必须成对：`spec.md`（WHAT/WHY，技术无关）+ `plan.md`（HOW，实现细节）。
3. `spec.md`：目的、问题、范围、用户故事、`FR-*`（RFC 2119）、实体、验收场景、非功能、假设、依赖。
4. `plan.md`：技术上下文、宪法合规、研究结论、数据模型、接口契约、实现策略、测试、文件清单、FR 交叉引用。
5. `plan.md` 必须回引 `spec.md` 的 FR；每条 FR 必须有落点。
6. 文档生成顺序：项目级 → 模块级（spec 先于 plan）→ 索引；索引必须扫描实际目录，不预测结构。
7. 链接必须可点；断链即缺陷。

---

## 第十二条 变更与豁免

1. 修改本宪法需在父工程 `specs/` 提交 `docs:` 变更，说明理由与影响范围。
2. 编号迁移属于宪法级变更：必须提供迁移对照表、更新所有引用、验证 0 断链。
3. 例外必须登记：在子工程 `SPECS_CHECKLIST.md` 写「未登记例外：无」；有例外则逐条写原因、出口、时限。
4. 本宪法与子工程宪法冲突时：**编号/分工**以本文件为准；**技术事实**以源码与子工程宪法为准。
